# Промпт для AI-агента: разработка программы «Image2GDRAM Converter» по ТЗ

## Роль и задача

Ты — ведущий разработчик C#/.NET (WPF) с опытом во встраиваемых системах: Keil C51/A51, STM32, монохромные графические дисплеи и организация их GDRAM. Твоя задача — самостоятельно и полностью разработать программу «Image2GDRAM Converter» версии 1.0 строго по техническому заданию из файла `specification.md` и подготовить весь комплект поставки из раздела 9 ТЗ: программу, исходники с инструкцией по сборке, документацию, тестовые изображения и эталонные массивы.

## 4. Архитектура (п. 4.6 ТЗ)

Конвейер из независимых модулей с узкими интерфейсами:

1. **Загрузка** (`IImageDecoder`): файл → список кадров RGBA, 8 бит на канал (собственный тип `RgbaImage`: ширина, высота, `byte[]`). ImageSharp используется **только здесь**, за интерфейсом, чтобы его можно было заменить (например, на WIC). Перед полным декодированием проверяй размер (`Image.Identify`) и отклоняй изображения больше 8192×8192 с понятным сообщением. Кадры анимированного GIF должны быть полностью скомпонованы (с учётом disposal) — проверь это тестом.
2. **Обработка:** шаги п. 4.1.2, каждый — отдельный класс с явными параметрами. На выходе — монохромный растр `MonoBitmap` (ширина, высота, признак активности пикселя). Поворот, масштабирование, перевод в серое и дизеринг реализуй **сам** над `RgbaImage`, не через ImageSharp: так результат детерминирован и не зависит от версии библиотеки.
3. **Упаковка** (`IPacker`): `MonoBitmap` + `PackingOptions` → `byte[]`. Помимо `Pack`, упаковщик предоставляет:
   - `Unpack(bytes, width, height, options)` — для импорта массивов шрифтов (п. 4.2.2, источник 4), с учётом инверсии и игнорированием битов дополнения;
   - `Locate(x, y)` → (индекс байта, номер бита) — для подсказки в сетке и подсветки байта в окне кода;
   - `GetSize(width, height, options)` — размер в байтах.
4. **Генерация вывода** (`IOutputGenerator`): C для C51, C для STM32, A51 (самостоятельный модуль и фрагмент для `$INCLUDE`), BIN. Генератор возвращает тексты файлов и **карту «индекс байта → позиция в тексте»** для подсветки байта при наведении на сетку.

**Расширяемость до цвета:** заложи в `PackingOptions` формат пикселя (`Mono1bpp`; место под `Rgb565` с порядком байтов `BigEndian`/`LittleEndian`) и выбирай упаковщик по формату через реестр или фабрику. Новый режим упаковки или формат вывода добавляется новым классом и регистрацией без правки остальных модулей. В интерфейсе 1.0 цветные режимы не показывай.

## 5. Точная семантика алгоритмов

### 5.1. Упаковка (разделы 3 и 4.3 ТЗ)

Обозначения: W×H — размер; `active(x, y)` — пиксель активен; x — столбец слева направо, y — строка сверху вниз. До инверсии: активный пиксель — бит 1, фон — 0, биты дополнения — 0. **Инверсия** применяется к итоговому байту целиком (`b ^= 0xFF`), включая биты дополнения и биты 7–6 в 6-битном режиме.

**Горизонтальный режим, b бит в байте (8 или 6).** Байтов в строке `B = ⌈W / b⌉`, всего `H × B`. Байт с индексом `y·B + j` содержит пиксели `x = j·b + k`, где `k = 0…b−1`; пиксели с `x ≥ W` — биты дополнения. LSB first: пиксель k → бит k. MSB first: пиксель k → бит `b − 1 − k` (бит 7 при b = 8, бит 5 при b = 6).

**Вертикальный режим.** Страниц `P = ⌈H / 8⌉`, всего `W × P` байт. Байт страницы p столбца x содержит пиксели `y = 8p + k`, `k = 0…7`; строки `y ≥ H` — биты дополнения. LSB first: k → бит k; MSB first: k → бит `7 − k`. Порядок обхода «по страницам» — индекс `p·W + x`; «по столбцам» — индекс `x·P + p`. При H ≤ 8 оба порядка совпадают.

**Шрифты.** Каждый символ — отдельный `MonoBitmap` размером в ячейку, упакованный тем же упаковщиком. Символ с кодом c занимает байты `c·N … c·N + N − 1`, где N — число байт на символ. Пустой символ — все биты фона: 0x00, а с инверсией 0xFF.

**Обязательные контрольные примеры в тестах:** один активный пиксель (0, 0) на фоне.

| Режим | Первый байт | С инверсией |
|---|---|---|
| вертикальный, LSB first | 0x01 | 0xFE |
| вертикальный, MSB first | 0x80 | 0x7F |
| горизонтальный, MSB first, 8 бит | 0x80 | 0x7F |
| горизонтальный, MSB first, 6 бит | 0x20 | 0xDF |

Также проверь таблицу п. 4.2.1, размеры массивов 1536 и 6144 байт, строку 240 пикселей = 40 байт в 6-битном режиме, спрайт 13×11 (некратность по обеим осям).

### 5.2. Конвейер изображения (п. 4.1)

- **Наложение на фон:** по каждому каналу `c' = (c·a + bg·(255 − a) + 127) / 255` в целых числах.
- **Поворот и отражение:** без потерь; сначала поворот, затем отражение. Поворот на 90/270° меняет местами ширину и высоту до шага масштабирования.
- **Масштабирование:** «с усреднением» — усреднение по площади (box/area-фильтр с учётом частичного покрытия пикселей); «ближайший сосед» — выборка по центрам пикселей. Обе реализации собственные и детерминированные.
- **Вписывание и выравнивание** — по п. 4.1.3: 9 позиций и смещение по X/Y. При центрировании нечётную разницу округляй в меньшую сторону (влево/вверх).
- **Яркость:** `Y = (299·R + 587·G + 114·B + 500) / 1000` в целых; `active = Y < threshold`.
- **Флойд — Стейнберг и Аткинсон:** классические коэффициенты, обход строк слева направо без «змейки»; квантование `out = (v < threshold) ? 0 : 255`, ошибка `v − out`. У Аткинсона распределяется 6/8 ошибки (по 1/8 на 6 соседей), остаток теряется.
- **Байер 4×4 и 8×8:** стандартные индексные матрицы M; `active = Y < threshold + 255·((M[y mod n][x mod n] + 0.5) / n² − 0.5)`.
- **Ручные правки** хранятся как разреженный набор переопределений `(x, y) → active` поверх результата бинаризации; для анимированного GIF — отдельно для каждого кадра. При изменении параметров шагов 1–5 правки сбрасываются после подтверждения. Если пользователь отказался — изменённый параметр откатывается к прежнему значению. Предупреждение показывается один раз: после сброса правок их больше нет и спрашивать не о чем.

Все выбранные формулы задокументируй в `docs/decisions.md` и в руководстве пользователя.

## 6. Пробелы и неоднозначности ТЗ — принятые решения

1. **Приложение А, неполные строки таблицы пресетов:**
   - WG240128A (T6963C): горизонтальное, MSB first, 8 бит, порядок обхода не применяется, 3840 байт, ЖКИ. Для режима шрифта FS = 6×8 пользователь вручную выбирает 6 бит в байте.
   - RG12864F (NT7108, совместим с KS0108): вертикальное, LSB first, 8 бит, по страницам, 1024 байта, ЖКИ. Деление на две половины по 64 столбца (два кристалла, CS1/CS2) выполняет драйвер дисплея — по аналогии с примечанием 2 о SH1106.
   - RET012864DGPP3N (SSD1305, раздел 2 ТЗ): вертикальное, LSB first, 8 бит, по страницам, 1024 байта, OLED.
   - Пресеты UC1608, NT7108 и SSD1305 отметь в `docs/decisions.md` как требующие сверки с datasheet и подтверждения заказчиком (примечание 1 приложения А).
   - Пресеты храни данными в одном месте (встроенный JSON или единая таблица), а не разбрасывай по коду.
2. **Название программы.** Пункт 1.1 называет её «Image2GDRAM Converter», а примеры приложения В — «Converter_image_IU 1.0». В заголовке-комментарии используй «Image2GDRAM Converter 1.0», вынеся строку в одну константу. Имена `settings.json`, `%APPDATA%\ImageIU` и расширение `.iiu` бери строго из ТЗ.
3. **Знак «×» отсутствует в CP1251**, а CP1251 — кодировка вывода по умолчанию. В генерируемых файлах вместо «×» всегда пиши латинскую `x` («ячейка 12x16 (ШxВ)», «256 символов x 24 байта = 6144 байта»), чтобы содержимое не зависело от кодировки. Остальное оформление приложения В воспроизводи точно: отступы, порядок строк, формат комментариев, вложенные фигурные скобки для шрифтов, метка `FONT_6X8` в верхнем регистре, сегмент `?CO?FONT_6X8`. Если имя исходного файла или гарнитуры содержит символы вне CP1251, заменяй их на `?` и предупреждай пользователя.
4. **Русские формы множественного числа** в заголовке: «1024 байта», «6144 байта», «1536 байт», «3840 байт», «1 байт». Реализуй правило склонения и покрой его тестом.
5. **Параметры упаковки на вкладках независимы.** У каждой вкладки свой пресет и свой набор параметров: шрифт для T6963C и картинка могут упаковываться по-разному. На вкладке шрифтов пресет задаёт только параметры упаковки и цветовую схему; размер определяется размером ячейки.
6. **Области, не покрытые изображением** (п. 4.1.3), заливаются цветом фона шага 1 (белым или чёрным) до перевода в оттенки серого.
7. **«Размер по исходному изображению»:** если исходник после поворота больше 1024 по любой оси, это ошибка валидации с подсказкой задать размер вручную (ограничение п. 4.3.5).
8. **Оформление шрифтов.** Правило п. 4.4.4 «каждый символ с новой строки; если байт больше 16 — перенос на несколько строк поровну» имеет приоритет над настройкой «байт в строке», которая применяется к изображениям: 24 байта → 2 строки по 12, 32 → 2 по 16.
9. **Числа в ассемблере.** Данные — всегда с ведущим нулём и двумя цифрами (`000h`, `07Ch`, `0FFh`), как в примере В.2; двоичный формат — `11111111b`. Код символа в комментарии — как в примере: `00h`, `7Fh`, `0C0h` (ведущий ноль только перед буквой). В C — `0x` и заглавные шестнадцатеричные цифры (`0x7C`).
10. **Комментарий с изображением символа.** Печатаемыми считай 0x20–0x7E и 0x80–0xFF, кроме 0x98, 0xA0 (неразрывный пробел) и 0xAD (мягкий перенос). В CP1251-файле символ пишется одним байтом, в UTF-8 — в UTF-8.
11. **Анимированный GIF, экспорт всех кадров:** двумерный массив `[число кадров][размер кадра]`; в `.h` дополнительно макросы `<ИМЯ>_FRAMES` и `<ИМЯ>_FRAME_SIZE`, а `<ИМЯ>_SIZE` — общий размер. BIN — кадры подряд.
12. **Ограничение C51:** если массив больше 65535 байт (возможно при 1024×1024 или экспорте всех кадров GIF), для целей C51/A51 показывай предупреждение; генерацию не блокируй.
13. **Имя массива по умолчанию:** латиница в нижнем регистре, прочие символы → `_`, повторы `_` схлопываются; при пустом результате — `image` или `font`; если начинается с цифры — префикс `img_`; затем суффикс размера (`_128x64`, `_6x8`); обрезка до 31 символа с сохранением суффикса.
14. **Ручные правки шрифта.** Символы, изменённые вручную, помечаются в обзорной таблице и при перегенерации из источника (TTF или лист) не перезаписываются. Есть команды «Вернуть символ к источнику» и «Сбросить все ручные правки». Смена размера ячейки и импорт массива заменяют всю таблицу после подтверждения, если есть правки. Ctrl+Z/Ctrl+Y работают и в редакторе символа.
15. **Растеризация TrueType.** Размер в пикселях — em-размер при 96 DPI (`pixelsPerDip = 1.0` явно). Результат не должен зависеть от масштаба экрана Windows и ClearType. Рекомендуемый путь: `FormattedText.BuildGeometry` (учитывает синтезированные жирный и курсив) → `GetFlattenedPathGeometry()` → собственная заливка полигонов по правилу nonzero. Без сглаживания — проверка центра пикселя; со сглаживанием — суперсэмплинг (например, 4×4) → покрытие → `Y = 255 − покрытие·255` → порог по п. 5.2. Начальное положение — левый край ячейки и базовая линия по метрикам шрифта, затем пользовательское смещение X/Y; всё, что выходит за ячейку, обрезается. Наличие глифа проверяй по `GlyphTypeface.CharacterToGlyphMap`. Геометрию глифов кэшируй: смена параметров упаковки не должна заново растеризовать шрифт.
16. **CP1251 в .NET 8:** при старте вызови `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`. Код 0x98 в CP1251 не занят — обрабатывай его явно, не полагаясь на таблицу .NET.
17. **Импорт массивов (п. 4.2.2, источник 4):**
    - числа: `0x1F`/`0X1F`; `1Fh`/`0C0h` (начинается с цифры, регистр любой); двоичные `01010101b` (только 0 и 1) и `0b01010101`; десятичные;
    - комментарии `/* */`, `//` и `;` игнорируются;
    - массив — это инициализатор `{ … }` после `=` (вложенные скобки разворачиваются) или непрерывная последовательность строк `DB` (метка начинает новый массив); строковые литералы в `DB` дают коды символов в CP1251;
    - значение вне 0…255 — ошибка с номером строки;
    - кодировка файла: сначала строгий UTF-8, при ошибке — CP1251.

## 7. Генерация кода: совместимость (п. 4.4)

- **C (оба варианта):** только блочные комментарии `/* */`, только шестнадцатеричные литералы, синтаксис C89. Файлы `.c` и `.h` — по образцу приложения В; `.c` подключает собственный `.h`.
- **Keil C51:** `unsigned char code name[...]` в `.c` и `extern unsigned char code name[...];` в `.h`. Для шрифтов — двумерный массив `[256][<ИМЯ>_BYTES_PER_CHAR]`.
- **STM32:** `const uint8_t` (по умолчанию, с `#include <stdint.h>` в `.h`) или `const unsigned char`; без `static`. Код без предупреждений в ARM Compiler 5/6, IAR EWARM и GCC (`-std=c99 -Wall -Wextra -pedantic`).
- **A51, самостоятельный модуль:** `PUBLIC NAME`, `?CO?NAME SEGMENT CODE`, `RSEG ?CO?NAME`, метка `NAME:`, строки `DB`, `END`. Имя — в верхнем регистре, как в примере В.2: C51 и A51 по умолчанию работают с внешними именами в верхнем регистре, поэтому `extern unsigned char code font_6x8[]` из C свяжется с меткой `FONT_6X8`. **Фрагмент для `$INCLUDE`:** только метка и строки `DB` — без `PUBLIC`, сегмента и `END`. Строка `DB` не заканчивается запятой.
- **Валидатор имени (п. 4.4.2):** ключевые слова C89/C99; расширения Keil C51 (`_at_`, `alien`, `bdata`, `bit`, `code`, `compact`, `data`, `far`, `idata`, `interrupt`, `large`, `pdata`, `_priority_`, `reentrant`, `sbit`, `sfr`, `sfr16`, `small`, `_task_`, `using`, `xdata`); для A51 — имена регистров (`A`, `AB`, `C`, `DPTR`, `PC`, `R0`–`R7`, `AR0`–`AR7`), все мнемоники 8051, директивы и операторы A51. Для A51 сравнение без учёта регистра.
- **Кодировка и переводы строк:** CP1251 или UTF-8 **без BOM**; CRLF везде, файл заканчивается CRLF. В буфер обмена — тот же текст.
- **Дата и время** в заголовке отключаемы, формат фиксированный: `yyyy-MM-dd HH:mm:ss`.
- **Детерминизм:** при отключённой дате повторная генерация даёт побайтно идентичные файлы — это проверяется тестом.
- Перед перезаписью существующего файла — подтверждение (п. 4.4.1).

## 8. Интерфейс (раздел 5 ТЗ) — технические указания

- **Окно:** минимум 1024×680, две вкладки, русский язык. `app.manifest` с `PerMonitorV2`; вёрстка без жёстких пиксельных размеров, ничего не обрезается при минимальном размере окна.
- **Строки интерфейса** — только во внешних словарях, ни одной строки интерфейса в XAML-разметке или C#-коде. Рекомендуется встроенный словарь `ResourceDictionary` для русского языка (`{DynamicResource}` в XAML, сервис локализации для кода) плюс загрузка дополнительных словарей из папки `Languages\` рядом с exe. Язык выбирается параметром в `settings.json`; так новый язык добавляется без пересборки. Если выберешь `.resx`, учти: при сборке через CLI класс-обёртка автоматически не генерируется.
- **Интерактивная сетка** — собственный контрол, рисующий в `WriteableBitmap` (или только видимую область через `DrawingVisual`). **Не создавай WPF-элемент на каждый пиксель** — при 1024×1024 это неприемлемо. Требования к сетке:
  - `RenderOptions.BitmapScalingMode="NearestNeighbor"`, `UseLayoutRounding`;
  - масштаб от 1:1 до 32:1 и «по размеру окна», прокрутка;
  - линии сетки включаются и выключаются; толстые линии на границах байтов и страниц — каждые 8 пикселей по направлению упаковки, при 6 битах в байте — каждые 6;
  - подсказка при наведении: X, Y, номер байта (dec/hex), номер бита, значение байта (hex/bin); подсветка этого байта в окне кода через карту позиций генератора;
  - рисование: щелчок переключает пиксель, протягивание ЛКМ рисует активные пиксели, ПКМ — фон; один штрих — одно действие для Ctrl+Z/Ctrl+Y;
  - цветовая схема «ЖКИ»/«OLED».
- **Окно кода:** только чтение, моноширинный шрифт, быстрая работа с текстом около 1 МБ (1024×1024 → 131072 байта → примерно 800 КБ текста). AvalonEdit подходит; `TextBox` допустим, если укладывается во временные требования.
- **Пересчёт** предпросмотра и кода — асинхронный, с отменой предыдущего (`CancellationToken`) и debounce примерно 30–50 мс. UI не подвисает при перетаскивании ползунка порога. Требования п. 5.1: не более 200 мс для изображений до 240×128 и таблиц шрифтов, не более 1 с для 1024×1024. Измерь время (`Stopwatch`) и приведи замеры в отчёте.
- **Валидация** через `INotifyDataErrorInfo` (`ObservableValidator`): недопустимые поля подсвечиваются сразу, сохранение и копирование блокируются, в окне кода выводится причина.
- **Надёжность:** обработчики `DispatcherUnhandledException`, `TaskScheduler.UnobservedTaskException` и `AppDomain.CurrentDomain.UnhandledException` показывают сообщение с причиной вместо аварийного завершения. Все файловые операции — с понятными сообщениями об ошибках. Исходные файлы никогда не изменяются.
- **Закрытие с несохранённым проектом:** «Сохранить / Не сохранять / Отмена».
- **Вкладка «Генератор шрифтов»:**
  - обзорная таблица 16×16 (строки — старший полубайт кода, столбцы — младший) с подписями; пустые и изменённые вручную символы визуально различимы;
  - редактор символа: переключение пикселей, очистка, инверсия, сдвиг на 1 пиксель в 4 стороны, копирование и вставка;
  - параметры источников и диапазонов; список символов, отсутствующих в шрифте;
  - предпросмотр строки (по умолчанию «Привет! Hello 123»).
- **Предупреждения** (отсутствующие глифы, несовпадение числа значений при импорте, превышение 64 КБ для C51 и т. п.) — в неблокирующей панели или строке состояния; модальные окна — только для подтверждений.

## 9. Настройки и проекты (п. 4.5)

- `settings.json` рядом с exe — путь через `AppContext.BaseDirectory`: в single-file публикации `Assembly.Location` пуст. Если записать туда нельзя (проверяй реальной попыткой записи), используй `%APPDATA%\ImageIU\settings.json`.
- Последние параметры сохраняются автоматически и восстанавливаются при запуске. Повреждённый `settings.json` не мешает запуску: сброс к умолчаниям и сообщение.
- Пользовательские пресеты можно создавать, переименовывать и удалять; встроенные неизменяемы.
- Проект `.iiu` (JSON, UTF-8) содержит: версию формата, путь к исходному файлу, все параметры обеих вкладок, ручные правки, для шрифта — все 256 символов. Если исходный файл при открытии проекта не найден — сообщение, параметры и правки всё равно загружаются.
- Сериализация — `System.Text.Json` через отдельные DTO (не сериализуй ViewModel напрямую), перечисления — строками.

## 10. Тестирование и эталоны (раздел 11 ТЗ)

**Модульные тесты (xUnit) ядра**, как минимум:

- **упаковщик:** все 16 допустимых комбинаций параметров на случайных растрах (фиксированный seed) разных размеров, включая некратные 8 и 6, 1×1 и 1024×1024; контрольные примеры из п. 5.1; согласованность `Locate` с `Pack`; `Unpack(Pack(b)) == b`; биты дополнения и инверсия;
- **независимая эталонная реализация упаковки** в тестовом проекте: максимально наивная, «по определению» из ТЗ, без общего кода с ядром; сравнение с ядром побайтно;
- **конвейер:** альфа-смешивание, повороты и отражения (по маркерам тестового изображения), режимы вписывания и выравнивания, оба алгоритма масштабирования, граница порога (Y = threshold − 1 и Y = threshold), повторяемость дизеринга;
- **генераторы:** «золотые» тесты против примеров приложения В с учётом решений 2 и 3 из раздела 6 (дата отключена); CRLF, отсутствие BOM, корректная перекодировка в CP1251, перенос строк шрифта, форматы `0FFh` и `11111111b`, склонение «байт/байта», валидатор имён;
- **шрифты:** таблица п. 4.2.1, пустые символы, диапазоны (включая исключение 0x98), импорт массивов из C и A51 (вложенные скобки, комментарии, несколько массивов, меньше и больше значений → предупреждение), лист символов с отступами и интервалами;
- **настройки и проекты:** сохранение → загрузка → идентичность.

Для ViewModel покрой тестами ключевые сценарии: смена пресета → «Пользовательский (на основе …)», сброс правок с подтверждением и откатом, undo/redo.

**Дымовая проверка компиляции:** скрипт `tools/compile-check.ps1`. Если доступен `gcc`, `clang` или `arm-none-eabi-gcc`, он компилирует сгенерированный вывод для STM32 с `-std=c99 -Wall -Wextra -pedantic -Werror`, а вывод для C51 — с `-Dcode=`. Если компиляторов нет, скрипт сообщает об этом и пропускает проверку.

**Тестовые изображения (приложение Б)** генерируй программно утилитой `tools/TestAssetsGenerator` строго по описанию:

- рамка толщиной 1 пиксель;
- 4 разных маркера 8×8 с отступом 2 пикселя от рамки;
- метки через каждые 8 пикселей (3 пикселя, каждая восьмая — 6);
- диагонали под 45°;
- шахматное поле 16×16 из клеток 1×1;
- закрашенный и пустой прямоугольники 16×16;
- надпись «240x128» или «128x64» — встроенным в утилиту растровым шрифтом 5×7, а не системным, чтобы результат не зависел от машины.

Элементы не перекрываются. Отдельно — `test_sprite_13x11.png` с несимметричной фигурой. Там же сгенерируй растровые листы шрифтов 6×8, 8×8 и 12×16 (PNG, 16 символов в строке): эталоны шрифтов строятся по ним, а не по системным TTF.

**Эталонные массивы.** Для каждого размера из пресетов приложения А, для `test_sprite_13x11.png` и для шрифтов трёх размеров — по всем допустимым комбинациям параметров упаковки:

- горизонтальный режим: порядок бит × бит в байте × инверсия = 8 комбинаций;
- вертикальный режим: порядок бит × порядок обхода × инверсия = 8 комбинаций.

Формируй `.bin` (и для наглядности `.c`) **независимой эталонной реализацией**, не кодом ядра, в `testdata/reference/`. Добавь описание `index.md`: какой вход, какие параметры, какой файл. Тест сравнивает вывод ядра с эталонами побайтно. В отчёте отметь, что эталоны требуют согласования с заказчиком.

**Запуск приложения:** после этапов с GUI запускай собранное приложение и убеждайся, что оно стартует без исключений.
